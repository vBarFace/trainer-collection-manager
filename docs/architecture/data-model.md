# Data model

## Implemented schema

`schema_migrations` records applied immutable migration versions. Version 1 creates `application_settings` for local metadata; version 2 adds inventory and seeds standard tags; version 3 adds appraisal IVs and the `SAVE/SPECIAL` standard tag; version 4 adds appraisal revision tracking and evaluation metadata; version 5 adds separately confirmed reference identity; version 6 adds strategic observation revision tracking. Version 7 adds confirmed lifecycle event history; version 8 extends its allowed action kinds with Power Up. Versions 1–7 are unchanged. Pending migrations run in order in one transaction and record their versions only on success. Reopening the database does not rerun applied migrations, reset revisions or reseed tags.

| Table                | Fields and constraints                                                                                                                                                                                                                                                                                                                                      |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pokemon`            | `id`: canonical lowercase UUID v4 primary key; `display_name`: required manual label; `cp`: optional positive SQLite integer; `iv_attack`, `iv_defense`, `iv_hp`: optional appraisal group, each 0–15; independent `appraisal_revision` and `strategic_observation_revision`: nonnegative integers, initially 0; `created_at`, `updated_at`: UTC timestamps |
| `tags`               | Integer primary key; `name`: required unique label using SQLite `NOCASE`; `scope`: `standard` or `local`; `created_at`: UTC timestamp                                                                                                                                                                                                                       |
| `pokemon_tags`       | Composite primary key (`pokemon_id`, `tag_id`); foreign keys with delete cascade; `created_at`: UTC timestamp                                                                                                                                                                                                                                               |
| `pokemon_appraisals` | `pokemon_id`: primary key and foreign key with delete cascade; `input_revision`: evaluated IV revision; `ruleset_version`: explicit engine version; `evaluated_at`: UTC timestamp                                                                                                                                                                           |

`pokemon_reference_identity` (migration 5) has a Pokémon UUID primary/foreign key with delete cascade, confirmed `species_query`, nullable `form_query`, grouped nullable `dataset_id`/`species_id`/`form_id` pins and `confirmed_at` UTC timestamp. No row means unknown identity. The snapshot itself is a native embedded JSON file, separate from player data. See [reference schema, resolution and updates](../development/reference-data.md).

The assignment primary key supports lookup by Pokémon; a reverse `(tag_id, pokemon_id)` index supports tag lookup and cascade cleanup. No speculative indexes or real game datasets are included.

## Validation and ownership

- The Rust repository generates UUID v4 identities from SQLite's native random bytes, setting version and variant bits. Identity never depends on a label, species, import order or row position. UUIDs are identifiers, not secrets. A primary key rejects collisions; errors are returned without overwriting an existing record. Update input contains no identity field; a database trigger also prohibits changing the UUID.
- A manual display name is not a species identifier. Names contain 1–100 Unicode scalar values; tag labels contain 1–50. Rust rejects leading/trailing Unicode whitespace and control characters. Inputs are rejected rather than silently normalized. SQL adds basic length/trim checks as a second boundary.
- CP is unknown (`NULL`) or a positive signed 64-bit integer. No game-specific maximum or inferred species/level relationship is assumed.
- Appraisal IVs are either all unknown (`NULL`) or all present, each an integer from 0 to 15. `iv_hp` is the appraisal HP IV, not current or maximum observed HP. Rust represents the group as `Option<AppraisalIvs>` and validates each value. SQLite range checks and a cross-column `CHECK` on the last added column enforce the same rules on inserts and updates, including direct SQL. Existing version 2 records retain their UUIDs, names, CP, timestamps and tag assignments; their IVs start unknown. Updating with `ivs: None` explicitly clears all three IVs.
- Every instance has zero or more tags; duplicate assignments cannot exist. Assignment and removal are idempotent for existing entities. Missing Pokémon/tags produce typed not-found errors. Deleting an instance or custom tag cascades only its assignments.
- Standard tags are `EVOLVE`, `POWER UP`, `ATTACKER`, `GYM DEF`, `ROCKET`, `PVP 1500`, `PVP 2500`, `TRANSFER`, `SAVE/SPECIAL`. They are migration-owned. `SAVE/SPECIAL` expresses the user's intent to retain a special Pokémon (for example, a shiny); it does not assert or automatically detect shiny status. Repository operations and database triggers prevent renaming, deletion, promotion of custom tags, or insertion of extra standard tags. Future migrations changing the standard set must explicitly revise these triggers.
- Migration 3 temporarily replaces the standard insert/update guards inside the migration transaction to seed `SAVE/SPECIAL`. If a custom tag already uses that name (ASCII case-insensitively), it is promoted to standard with canonical spelling, preserving its identifier, creation timestamp and assignments. Other custom tags are unchanged. The guards are restored before commit; a failure rolls the migration back.
- Custom tags belong to this local application database (`scope = local`), with no account or remote ownership. Names share one unique namespace with standard tags. SQLite `NOCASE` folds ASCII case only: `Favorites` and `FAVORITES` collide; Unicode case variants and differently normalized Unicode strings remain distinct. Custom tags can be renamed and deleted, but cannot claim a reserved standard name.
- Timestamps use SQLite `CURRENT_TIMESTAMP` (UTC, second precision). Creation timestamps are preserved by repository updates; Pokémon `updated_at` is set on full updates or actual CP/IV corrections, and can equal its prior value within a second. Unchanged CP/IV corrections preserve timestamps. Custom tags currently record creation only. Full updates use SQLite serialization and last successful write wins. Narrow correction APIs compare expected values before writing; CP additionally requires the expected strategic observation revision. S2.2 adds history for confirmed evolution and targeted re-observation only; ordinary corrections are not retroactively audited.

## Confirmed lifecycle events (S2.2–S2.3)

### S2.3 Power Up invariants

Migration 8 extends the existing lifecycle table's allowed kinds with `power_up`, preserving event payloads, timestamps, request UUIDs, row ordering, foreign-key cascade and immutability. Migrations 1–7 remain unchanged. A Power Up targets one existing UUID and requires explicit in-game confirmation plus the expected observation revision. Optional manually entered CP is a positive signed 64-bit integer; null means keep the saved CP, including null when unknown. The CP update and one confirmed event commit atomically. UUID, identity/form, IVs, appraisal, tags and unrelated individuals remain unchanged. CP changes advance the existing observation revision; an event without changed observations does not. A globally unique request UUID prevents repeated confirmation even without a CP change. No resource inventory or persisted spending model exists, so this increment adds no costs, inferred level or statistics, or screenshot pipeline.

Migration 7 creates `pokemon_lifecycle_events`: globally unique confirmed request UUID primary key, individual UUID foreign key with delete cascade, checked `evolution` / `reobservation` kind, validated JSON event payload and SQLite UTC confirmation timestamp. An individual index supports history reads; a trigger rejects event updates. Pending actions exist only in renderer memory and never enter this table. Deleting an individual through the existing repository removes its history; this is not a permanent external audit ledger.

Each payload includes request/individual IDs, before/after identity and species/form pins, exact decimal CP and grouped IVs, per-patch screenshot/manual provenance, reviewed identity/individual confirmation and dataset/version context. The returned timestamp comes from the table. Existing records lack historical field provenance; snapshots do not retroactively infer it. Unknown values remain null and evolution records CP invalidation.

Immediate transactions validate expected strategic observation revision, mutation and event insertion together. The request UUID prevents replay even when a confirmed screenshot leaves all values unchanged; history alone does not advance observation revision. Evolution checks catalog ID/version and its direct target again, then changes identity and clears CP. Existing triggers can advance observation revision once for CP and once for identity; an evolution-only fallback increments it if a changed species pin has identical query text and the triggers advanced nothing. The counter tracks confirmed observations, not action sequence. IV appraisal revision is unchanged by evolution. Screenshot updates compare the exact reviewed identity and change only opted-in CP/IV values. Neither operation creates an individual.

## Native persistence boundary

`InventoryRepository::open` initializes/migrates the local database and enables foreign keys/WAL on its own connection. Production callers must use Tauri's resolved per-user app-data path. The path is a native API parameter only, never accepted from the renderer. Startup opens that same repository for the Inventory UI behind typed commands and serialized native access.

Typed APIs provide inventory CRUD, tag management, CP/IV/identity correction and appraisal evaluation. `PokemonId` validates canonical UUID v4 strings; `PokemonInput` contains only editable fields, including `ivs: Option<AppraisalIvs>` with `attack`, `defense` and `hp`. Errors distinguish invalid input, missing records, conflicting corrections, duplicate tag names, immutable standard tags and storage failures. Listing uses creation time then UUID for deterministic order; it currently returns all records without pagination.

All queries and bound parameters remain in Rust. No arbitrary SQL, SQL plugin or generic database Tauri command is exposed. The three Task 003 review commands are preserved; Task 005 adds `evaluate_pokemon` with a validated Pokémon UUID. `create_with_tags` atomically creates a record and its assignments, `snapshot` reads records/tags/evaluation state consistently, and evaluation atomically reads confirmed inputs and replaces appraisal metadata. CP and tag IDs cross IPC as decimal strings to preserve the full SQLite integer range. See [manual review](../development/screenshot-review.md) and [evaluation](../development/evaluation.md) for native contracts. There are no image blobs, external identifiers, account fields or network calls.

The saved-IV correction follow-up adds `correct_pokemon_ivs(id, { expectedIvs, ivs })`, restricted by the same main-window ACL. Both groups must be explicit `null` or complete attack/defense/HP integer objects; omission, partial groups and unrelated fields are rejected. `correct_ivs` validates both groups and uses an immediate write transaction to read and compare current IVs with the expected group. Different values produce a conflict without changing data. Matching values permit updating only IVs and `updated_at` when needed, while preserving name, CP, UUID, creation time, tag assignments and existing appraisal metadata. Its existing value-based conflict contract remains: a change/revert restoring the expected IV group is accepted. Actual IV changes independently advance both appraisal and strategic revisions; no-op confirmations advance neither.

## Saved CP and strategic observations (S2.1)

`correct_pokemon_cp(id, { expectedCp, expectedStrategicObservationRevision, cp })` is a narrow main-window command. Both CP fields must be explicitly present as canonical positive decimal strings or `null` for unknown. The expected revision is a required canonical nonnegative decimal string. Rust rejects malformed values, leading zeros, zero/negative CP, fractions, overflow, missing fields and unrelated fields. CP covers 1–9223372036854775807; revisions cover 0–9223372036854775807. JSON/TypeScript expose `strategicObservationRevision` as a string, without converting it or CP through JavaScript Number. Revision counters are internal concurrency data, not normal UI text.

An immediate transaction reads the selected UUID and compares both current CP and strategic revision before any write. A mismatch rejects even a requested no-op; a CP change followed by a revert cannot revive a stale draft. Missing/deleted individuals, invalid values, conflicts and revision overflow make no changes. Matching no-op confirmations preserve revision and `updated_at`. An actual correction changes only CP, `updated_at` and the strategic revision, preserving UUID, display name, IVs, identity/pins, tags, creation time and appraisal metadata/results. It never runs or invalidates `appraisal-1` and infers no level, spending, moves, action history or usefulness.

Migration 6 gives old and new records strategic revision 0 without rewriting existing observations or timestamps. Null-safe SQLite triggers advance it on actual CP or grouped IV changes, including full native updates, and on insertion, deletion or a change of the exact confirmed `(species_query, form_query)` identity association. A single Pokémon update that changes both CP and IVs advances the strategic revision once. Unknown identity differs from a confirmed identity; changing confirmed text, even to another alias, is an observation correction. Dataset pins, dataset/provenance refreshes, catalog activation and resolution changes alone are not player-confirmed identity observations and do not advance the revision. Reads, appraisal evaluation, display labels and tags also leave it unchanged. Overflow aborts the statement and enclosing correction transaction rather than wrapping or rounding.

The persisted monotonic counter detects same-second changes and change/revert sequences and survives reopening. Existing IV/identity expected-value conflict checks remain intact. This is infrastructure for future strategic invalidation; there is no strategic evaluation, automatic recalculation, goal/budget/protection revision or lifecycle event log in S2.1. Correcting an identity association records corrected data; it does not claim that an evolution occurred.

## Appraisal lifecycle and reproducibility

Migration 4 preserves Pokémon UUIDs, values, timestamps and tag assignments. Existing and newly imported records have revision 0 and no appraisal row, so they start pending. The table stores only the latest attempt metadata, including attempts with insufficient data; it is not an evaluation history.

| State        | Derived condition                                                                                    |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| `pending`    | No persisted appraisal attempt exists.                                                               |
| `evaluated`  | Attempt revision and ruleset match; all three confirmed IVs are known and appraisal rules complete.  |
| `needs_data` | Attempt revision and ruleset match; the confirmed IV group is unknown.                               |
| `stale`      | Persisted attempt revision or ruleset differs from the current revision or supported engine version. |

A null-safe SQLite trigger increments `appraisal_revision` when at least one actual IV changes, including clearing/adding the group. Unchanged IV writes, display-name/CP changes and tag changes do not invalidate appraisal. Revision comparison detects changes within one timestamp second and remains stale after a change/revert. Attempts that previously needed data also become stale after relevant changes. Missing/deleted Pokémon return typed errors; deleting a Pokémon cascades its appraisal metadata.

The `appraisal-1` engine calculates facts from confirmed structured data only. Totals, percentages, perfect findings and lifecycle state are derived in Rust, never duplicated in SQLite or React. Current inputs plus matching metadata reproduce the same result. No old-input snapshot is retained: stale result details are withheld, while their version/timestamp remain available; re-evaluation replaces metadata and derives a current result. An engine change must change its ruleset version. The current metadata schema supports appraisal only; strategic analysis needs a separate explicit scope/version contract.

Typed findings and future recommendations keep stable codes, observations, explanations, ruleset provenance and limitations/missing data separate from assigned tags. Recommendation action/classification may be absent. The current engine emits no recommendations or suggested tags and never modifies assignments. See [decision 0005](../decisions/0005-persisted-appraisal-evaluation.md).

## Deferred fields and derived data

Species/form identifiers and reference provenance are implemented as a separate association/snapshot contract, but no real game metadata is bundled. Observed HP, shiny status, second-attack state, fast/charged moves, level, capture details, observation provenance and import validation state remain deferred. Appraisal IVs are separate from species base stats, moves and observed CP/HP. This layer stores observed CP and appraisal IVs without calculating their relationship. Second attacks must be explicit structured fields if introduced, never inferred from tags. Imported screenshot data must be user-reviewed before persistence; original image files must not be retained by default.

Strategic recommendations, rankings and teams remain future derived data. They require validated species/form identity, applicable moves/level and other observations, licensed and versioned game data, and validated formulas with explicit versions. User intent/resources must be supplied when applicable. Appraisal completion does not imply PvP, PvE, gym, Rocket, investment or transfer analysis. No real game dataset, AI, cloud or telemetry is introduced. Local OCR remains temporary; confirmed structured import, identity associations and appraisal metadata are persisted.

## Proposed strategic assessments and roadmaps (Task 008)

Proposal only, except the S2.1 observation revision described above: migration 6 is the latest implemented schema. The following names describe logical records, not added plan tables, DTOs or commands. Start with one selected goal and one active plan per Pokémon, preserving multiple role assessments and alternative paths in the plan. Exact plan column/JSON layout is deferred to the persistence increment.

| Logical record                   | Minimum proposed contents and invariants                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Confirmed strategic observations | Existing Pokémon UUID; confirmed species/form pin, CP, grouped IVs and applicable new move/second-attack, level/evidence and individual-property fields. Each unknown is explicit; confirmation source/time distinguishes user-confirmed values from calculations. No image, raw OCR, file path or account identifier.                                                                                                                            |
| Strategic revision               | Monotonic native-owned revision per individual, incremented by actual changes to any strategically relevant observation, including identity association. It detects same-second changes and change/revert; no-op confirmations preserve it. It is independent of IV-only `appraisal_revision`.                                                                                                                                                    |
| Selected goal and constraints    | Named role/context, user target/preferences, budget per resource (unknown distinct from zero), collection protections and permission for irreversible evolution; independent monotonic revision on actual changes. Preserve the budget's confirmation time; do not decrement it from estimated spending.                                                                                                                                          |
| Plan snapshot                    | Native-generated plan ID, Pokémon UUID, generation time, goal/context/constraint snapshot and revision, observation revision and minimal consumed inputs, current/potential role assessments and readiness, missing inputs/assumptions, selected alternative, steps, expected benefit/limitations and suggested action/summary tag with kind.                                                                                                     |
| Step/alternative                 | Plan-local stable step ID, action kind, exact evolution target where relevant, required/optional flag, earlier prerequisite IDs, condition and its satisfaction evidence, target with units/context/calculation version, required/optional moves, estimated per-resource costs or unknowns, expected benefit and completion evidence. Alternatives are short ordered lists, not arbitrary graphs; every prerequisite precedes its dependent step. |
| Provenance envelope              | Strategic contract and ruleset versions; all consumed dataset IDs, versions, upstream revisions and content digests; mechanics version/digest; model version/digest and feature schema or explicit deterministic-only mode. Version identity is distinct from a player's observation revision.                                                                                                                                                    |
| Progress evidence                | Step action report/time and optional short user note, separately linked confirmed observation revision/fields/time, and separate confirmed resource spending if supplied. Record whether completion evidence matches the target. A report alone never changes stats or proves spending.                                                                                                                                                           |

Propose two native-owned plan slots per UUID: **current** and **previous**, each with its bounded structured snapshot and step evidence. A successful re-evaluation atomically replaces current and rotates its predecessor into previous; discard the older previous plan. Limit step/alternative counts and note sizes in the future contract. Preserve only consumed structured inputs, including explicit unknowns; never retain screenshots by default. This supports comparison and explains stale progress without an unbounded event log. It cannot reconstruct full history or rerun old calculations if their data/model artifacts are unavailable; label historical explanations accordingly. Do not retain duplicate external datasets or model weights in the player database.

Future saves/progress updates must include expected observation, goal and current-plan/progress revisions. Rust compares them in the same transaction as the write; conflicts and deleted individuals change nothing and require reload. A progress-only edit increments a separate plan/progress revision rather than the observation revision. Identical retried action reports are idempotent. Re-evaluation computes against an input/version snapshot and checks it again before publishing; a concurrent correction or catalog switch cannot install an already outdated plan. A failed evaluation/rotation preserves both slots. Evolution confirmation updates identity for the same UUID without creating a replacement inventory record; unknown resulting fields must not retain obsolete pre-evolution CP/moves as confirmed current values.

### Validity and progress rules

Readiness belongs to a role/context; validity belongs to a plan. Derive validity in Rust with explicit reasons: **invalid** for unsupported contracts or known impossible paths; otherwise **stale** for any consumed observation/goal/resource/protection or dataset/mechanics/rules/model version mismatch; otherwise **blocked** for missing required facts, unverified hard budgets or a prerequisite that prevents the next required action from safely proceeding; otherwise **current**. Ordinary unfinished future prerequisites block only dependent steps: a fully costed, eligible evolve-first path can remain current and suggest `EVOLVE`. Unknown downstream eligibility/costs still block investment because whole-path feasibility is unproven. Recheck the envelope on load/restart as well as before any progress write. A plan can retain blocking reasons while stale. Do not display stale/invalid suggestions as current instructions.

Each step starts suggested, can be user-reported done, then can be observation-confirmed only when the required post-action fields satisfy the target under valid mechanics. These are evidence states, not automatic game verification. Missing evidence blocks dependents. Required verified steps determine goal completion after re-evaluation; optional steps do not prevent use now. Undoing a report changes progress evidence only. Actual corrections require the observation confirmation flow. Confirming resulting observations may stale the plan; re-evaluation then reconciles the achieved target and any remaining steps.

Re-evaluation compares old/new inputs, targets and explanations. Keep previous reports in the previous slot. Offer compatible prior actions for explicit review, but never silently copy done flags to regenerated steps or use plan-local IDs as cross-version proof. Changed goals/resources can remove, reorder or invalidate paths; new data/rules/model versions can alter suitability. New protections take effect immediately. Changes to unrelated display labels have no strategic effect. Assigned tags never become model labels or verified facts; explicit retain/protection intent must nevertheless participate in constraints and invalidate conflicting plans.

The existing appraisal row and `appraisal_revision` remain untouched by identity, CP, move, level, goal or model changes. An actual IV correction can invalidate both scopes independently. Task 008 introduced no migration, runtime persistence or progress UI; S2.1 subsequently implements only saved CP correction and persisted observation revision. See [decision 0007](../decisions/0007-individual-progression-roadmaps.md).
