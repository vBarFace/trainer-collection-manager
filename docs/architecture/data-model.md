# Data model

## Implemented schema

`schema_migrations` records applied immutable migration versions. Version 1 creates `application_settings` for local metadata; version 2 adds inventory and seeds standard tags; version 3 adds appraisal IVs and the `SAVE/SPECIAL` standard tag; version 4 adds appraisal revision tracking and evaluation metadata; version 5 adds separately confirmed reference identity. Versions 1–4 are unchanged. Pending migrations run in order in one transaction and record their versions only on success. Reopening the database does not rerun applied migrations or reseed tags.

| Table                | Fields and constraints                                                                                                                                                                                                                                                                                    |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pokemon`            | `id`: canonical lowercase UUID v4 primary key; `display_name`: required manual label; `cp`: optional positive SQLite integer; `iv_attack`, `iv_defense`, `iv_hp`: optional appraisal group, each 0–15; `appraisal_revision`: nonnegative integer, initially 0; `created_at`, `updated_at`: UTC timestamps |
| `tags`               | Integer primary key; `name`: required unique label using SQLite `NOCASE`; `scope`: `standard` or `local`; `created_at`: UTC timestamp                                                                                                                                                                     |
| `pokemon_tags`       | Composite primary key (`pokemon_id`, `tag_id`); foreign keys with delete cascade; `created_at`: UTC timestamp                                                                                                                                                                                             |
| `pokemon_appraisals` | `pokemon_id`: primary key and foreign key with delete cascade; `input_revision`: evaluated IV revision; `ruleset_version`: explicit engine version; `evaluated_at`: UTC timestamp                                                                                                                         |

`pokemon_reference_identity` (migration 5) has a Pokémon UUID primary/foreign key with delete cascade, confirmed `species_query`, nullable `form_query`, grouped nullable `dataset_id`/`species_id`/`form_id` pins and `confirmed_at` UTC timestamp. No row means unknown identity. The snapshot itself is a native embedded JSON file, separate from player data. See [reference schema, resolution and updates](../development/reference-data.md).

The assignment primary key supports lookup by Pokémon; a reverse `(tag_id, pokemon_id)` index supports tag lookup and cascade cleanup. No speculative indexes or real game datasets are included.

## Validation and ownership

- The Rust repository generates UUID v4 identities from SQLite's native random bytes, setting version and variant bits. Identity never depends on a label, species, import order or row position. UUIDs are identifiers, not secrets. A primary key rejects collisions; errors are returned without overwriting an existing record. Update input contains no identity field; a database trigger also prohibits changing the UUID.
- A manual display name is not a species identifier. Names contain 1–100 Unicode scalar values; tag labels contain 1–50. Rust rejects leading/trailing Unicode whitespace and control characters. Inputs are rejected rather than silently normalized. SQL adds basic length/trim checks as a second boundary.
- CP is unknown (`NULL`) or a positive signed 64-bit integer. No game-specific maximum or inferred species/level relationship is assumed.
- Appraisal IVs are either all unknown (`NULL`) or all present, each an integer from 0 to 15. `iv_hp` is the appraisal HP IV, not current or maximum observed HP. Rust represents the group as `Option<AppraisalIvs>` and validates each value. SQLite range checks and a cross-column `CHECK` on the last added column enforce the same rules on inserts and updates, including direct SQL. Existing version 2 records retain their UUIDs, names, CP, timestamps and tag assignments; their IVs start unknown. Updating with `ivs: None` explicitly clears all three IVs.
- Every instance has zero or more tags; duplicate assignments cannot exist. Assignment and removal are idempotent for existing entities. Missing Pokémon/tags produce typed not-found errors. Deleting an instance or custom tag cascades only its assignments.
- Standard tags are `EVOLVE`, `POWER UP`, `ATTACKER`, `GYM DEF`, `ROCKET`, `PVP 1500`, `PVP 2500`, `TRANSFER`, `SAVE/SPECIAL`. They are migration-owned. `SAVE/SPECIAL` expresses the user's intent to retain a special Pokémon (for example, a shiny); it does not assert or automatically detect shiny status. Repository operations and database triggers prevent renaming, deletion, promotion of custom tags, or insertion of extra standard tags. Future migrations changing the standard set must explicitly revise these triggers.
- Migration 3 temporarily replaces the standard insert/update guards inside the migration transaction to seed `SAVE/SPECIAL`. If a custom tag already uses that name (ASCII case-insensitively), it is promoted to standard with canonical spelling, preserving its identifier, creation timestamp and assignments. Other custom tags are unchanged. The guards are restored before commit; a failure rolls the migration back.
- Custom tags belong to this local application database (`scope = local`), with no account or remote ownership. Names share one unique namespace with standard tags. SQLite `NOCASE` folds ASCII case only: `Favorites` and `FAVORITES` collide; Unicode case variants and differently normalized Unicode strings remain distinct. Custom tags can be renamed and deleted, but cannot claim a reserved standard name.
- Timestamps use SQLite `CURRENT_TIMESTAMP` (UTC, second precision). Creation timestamps are preserved by repository updates; Pokémon `updated_at` is set on full updates or actual IV corrections, and can equal its prior value within a second. An unchanged IV correction is a no-op and preserves timestamps. Custom tags currently record creation only. Full updates use SQLite serialization and last successful write wins. The narrower correction API compares the current IV group against expected values before writing; there is no general edit-history or revision-token contract.

## Native persistence boundary

`InventoryRepository::open` initializes/migrates the local database and enables foreign keys/WAL on its own connection. Production callers must use Tauri's resolved per-user app-data path. The path is a native API parameter only, never accepted from the renderer. Startup opens that same repository for the Inventory UI behind typed commands and serialized native access.

Typed APIs provide inventory CRUD, tag management, IV-only correction and appraisal evaluation. `PokemonId` validates canonical UUID v4 strings; `PokemonInput` contains only editable fields, including `ivs: Option<AppraisalIvs>` with `attack`, `defense` and `hp`. Errors distinguish invalid input, missing records, conflicting IV corrections, duplicate tag names, immutable standard tags and storage failures. Listing uses creation time then UUID for deterministic order; it currently returns all records without pagination.

All queries and bound parameters remain in Rust. No arbitrary SQL, SQL plugin or generic database Tauri command is exposed. The three Task 003 review commands are preserved; Task 005 adds `evaluate_pokemon` with a validated Pokémon UUID. `create_with_tags` atomically creates a record and its assignments, `snapshot` reads records/tags/evaluation state consistently, and evaluation atomically reads confirmed inputs and replaces appraisal metadata. CP and tag IDs cross IPC as decimal strings to preserve the full SQLite integer range. See [manual review](../development/screenshot-review.md) and [evaluation](../development/evaluation.md) for native contracts. There are no image blobs, external identifiers, account fields or network calls.

The saved-IV correction follow-up adds `correct_pokemon_ivs(id, { expectedIvs, ivs })`, restricted by the same main-window ACL. Both groups must be explicit `null` or complete attack/defense/HP integer objects; omission, partial groups and unrelated fields are rejected. `correct_ivs` validates both groups and uses an immediate write transaction to read and compare current IVs with the expected group. Different values produce a conflict without changing data. Matching values permit updating only IVs and `updated_at` when needed, while preserving name, CP, UUID, creation time, tag assignments and existing appraisal metadata. The comparison is value-based: a change/revert restoring the expected group is accepted. Existing revision invalidation handles actual corrections; no new migration is introduced.

## Appraisal lifecycle and reproducibility

Migration 4 preserves Pokémon UUIDs, values, timestamps and tag assignments. Existing and newly imported records have revision 0 and no appraisal row, so they start pending. The table stores only the latest attempt metadata, including attempts with insufficient data; it is not an evaluation history.

| State        | Derived condition                                                                                    |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| `pending`    | No persisted appraisal attempt exists.                                                               |
| `evaluated`  | Attempt revision and ruleset match; all three confirmed IVs are known and appraisal rules complete.  |
| `needs_data` | Attempt revision and ruleset match; the confirmed IV group is unknown.                               |
| `stale`      | Persisted attempt revision or ruleset differs from the current revision or supported engine version. |

A null-safe SQLite trigger increments `appraisal_revision` when at least one actual IV changes, including clearing/adding the group. Unchanged IV writes, display-name/CP changes and tag changes do not invalidate appraisal. Revision comparison detects changes within one timestamp second and remains stale after a change/revert. Attempts that previously needed data also become stale after relevant changes. Missing/deleted Pokémon return typed errors; deleting a Pokémon cascades its appraisal metadata.

The `appraisal-1` engine calculates facts from confirmed structured data only. Totals, percentages, perfect findings and lifecycle state are derived in Rust, never duplicated in SQLite or React. Current inputs plus matching metadata reproduce the same result. No old-input snapshot is retained: stale result details are withheld, while their version/timestamp remain available; re-evaluation replaces metadata and derives a current result. An engine change must change its ruleset version. The current metadata schema supports appraisal only; strategic analysis needs a separate explicit scope/version contract.

Typed findings and future recommendations keep stable codes, observations, explanations, ruleset provenance and limitations/missing data separate from assigned tags. Recommendation action/classification may be absent. The current engine emits no recommendations or suggested tags and never modifies assignments. See [decision 0005](../decisions/0005-persisted-appraisal-evaluation.md).

## Deferred fields and derived data

Species/form identifiers and reference provenance are implemented as a separate association/snapshot contract, but no real game metadata is bundled. Observed HP, shiny status, second-attack state, fast/charged moves, level, capture details, observation provenance and import validation state remain deferred. Appraisal IVs are separate from species base stats, moves and observed CP/HP. This layer stores observed CP and appraisal IVs without calculating their relationship. Second attacks must be explicit structured fields if introduced, never inferred from tags. Imported screenshot data must be user-reviewed before persistence; original image files must not be retained by default.

Strategic recommendations, rankings and teams remain future derived data. They require validated species/form identity, applicable moves/level and other observations, licensed and versioned game data, and validated formulas with explicit versions. User intent/resources must be supplied when applicable. Appraisal completion does not imply PvP, PvE, gym, Rocket, investment or transfer analysis. No real game dataset, AI, cloud or telemetry is introduced. Local OCR remains temporary; confirmed structured import, identity associations and appraisal metadata are persisted.
