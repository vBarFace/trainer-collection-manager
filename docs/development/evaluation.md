# Appraisal evaluation

Task 005 introduces an offline, deterministic appraisal workflow. It evaluates confirmed structured IVs only; it does not run screenshot extraction or read temporary review suggestions.

Task 006 adds a separate [reference context](reference-data.md) to the pure native evaluation boundary and displays available species/form metadata in Inventory. Missing reference data does not affect IV appraisal. No strategic formula is enabled; `appraisal-1` and its invalidation rules are unchanged.

## Using Inventory

1. Confirm a screenshot review to save a new pending record, or select an existing record.
2. Review its appraisal state, confirmed IVs and assigned tags.
3. Request an appraisal evaluation. The UI shows progress and offers retry on failure.
4. Read the resulting observed facts, findings, missing data and limitations. Re-evaluate after an IV or ruleset change.

The four states are **Pending**, **Evaluated**, **Needs data** and **Stale**. They apply to appraisal only. Evaluation metadata survives reopening the app; tags do not determine state. Saved appraisal IVs can be corrected as described below; full saved-record editing remains deferred.

## Correcting saved IVs

Select a record, then choose **Correct saved IVs**. Review the prefilled attack/defense/HP group and enter all three whole numbers from 0 to 15. To clear known values, choose **Mark all IVs unknown** or leave all three empty. Both are draft changes until **Confirm IV correction** is submitted. Partial groups are rejected. **Cancel IV correction** and switching to another record discard the unsaved draft.

Saving changes only IVs, preserving the record's UUID, name, CP, creation timestamp and tags. Actual changes update the record timestamp and make an existing appraisal attempt Stale through the existing migration-4 trigger. Unchanged values are a no-op, preserving timestamps and state. A record without an appraisal attempt remains Pending. Re-evaluate explicitly after correction; saving never runs appraisal or assigns tags.

The form disables duplicate submission, record selection, evaluation and cancellation while saving. Ordinary failures retain the draft for retry. If saved IVs changed while the draft was open, the native command rejects the save; discard the draft and reload, or cancel. A deleted record likewise requires reload. Drafts stay in memory and are not recovered after leaving the screen or closing the app. No screenshot is required.

`correct_pokemon_ivs` accepts a validated Pokémon UUID and `{ expectedIvs, ivs }`, with both groups explicitly supplied as `null` or complete integer groups. Rust validates both groups and compares current IV values with `expectedIvs` in an immediate write transaction before changing only IV columns. This is a value comparison, not a revision-token contract: an intervening change/revert that restores the expected group is accepted. No new migration, dependency or appraisal ruleset is needed.

## Ruleset `appraisal-1`

The repository accepts either a complete attack/defense/HP IV group or an unknown group. Each known value is 0–15. The engine reports those observed IVs, their total (0–45), and descriptive appraisal percentage (`total × 100 / 45`, displayed to two decimal places). A 15/15/15 group produces a perfect-appraisal finding. An unknown group produces explicit missing attack/defense/HP data instead of a percentage or guessed values.

The percentage describes appraisal only. It is not a PvP ranking, PvE strength score, overall quality score or transfer criterion. A perfect appraisal does not establish universal competitive superiority. Species, moves, level, game meta, shiny status and user preferences are not inferred. No transfer, evolve, power-up or other strategic recommendation is emitted, and no suggested tag is applied. Findings, future recommendations and already assigned tags remain distinct.

## Persistence and invalidation

Migration 4 adds a native-owned IV revision and one appraisal metadata row per evaluated Pokémon. The row records evaluated revision, ruleset version and UTC timestamp, including Needs data attempts. Lifecycle state and descriptive results are recalculated in Rust. No screenshot, path, raw OCR text, draft extraction, duplicated result or old-input snapshot is stored.

Actual IV changes increment the revision through a null-safe SQLite trigger. Name, CP and tag changes are outside this scope. Revision or ruleset mismatch makes the previous attempt Stale, including a previous Needs data attempt. Stale results are withheld until re-evaluation; their prior timestamp/version remain available. Re-evaluation replaces the latest attempt atomically. There is no evaluation history. Deleting a Pokémon cascades its appraisal metadata.

`evaluate_pokemon` accepts a canonical lowercase UUID v4 through the existing typed Tauri boundary and local main-window ACL. Rust owns validation, SQL and business rules. Invalid IDs and missing/deleted Pokémon fail safely. No frontend SQL or external game data is involved.

## Prerequisites for strategic evaluation

Future PvP, PvE, gym, Rocket, investment and transfer support requires its own scope and ruleset contract. Prerequisites include validated species/form identification, relevant confirmed moves/level and other observations, reviewed licenses and provenance for versioned game datasets, validated formulas and explicit user goals/resources where applicable. CP or aggregate IV percentage alone cannot justify transfer, evolution or power-up. Recommendation codes, actions/classifications, supporting facts, explanations, versions and limitations must remain separate from assigned tags.

The current increment adds no dependency, game dataset or third-party asset. Representative OCR accuracy measurement and wider layout support remain separate work; the existing single supplied screenshot does not establish recognition accuracy. See [data model](../architecture/data-model.md), [decision 0005](../decisions/0005-persisted-appraisal-evaluation.md) and [validation results](validation.md).

## Proposed strategic and learning evaluation (Task 008)

This is a research/release plan, not an implemented engine, trained model, collected dataset or achieved benchmark. Appraisal tests and OCR measurements do not establish strategic accuracy. The [PRD](../product/PRD.md#utility-classification-and-progression-roadmaps--proposed) defines behavior; [decision 0007](../decisions/0007-individual-progression-roadmaps.md) assigns domain ownership.

### Data and labels

| Evidence purpose                   | Required data and label source                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Facts and mechanics                | Reviewed species/form IDs, types/base stats, applicable individual properties, moves and availability, combat/stat/level calculations, evolution eligibility and investment costs, all versioned with source and rights evidence. Schema-1 evolution text alone is insufficient.                                                                                                                                                                                                      |
| Current/potential role suitability | Confirmed structured individual states and explicit goals/contexts paired with a reviewed rubric. Label current state and each feasible resulting state separately: suitable, unsuitable or unknown, with rationale and limitations. Use independent reviewers and adjudicate disagreements; retain uncertainty rather than forcing negatives. Permitted original observations, validated simulations and consented expert contributions may support labels after factual validation. |
| Preferences between paths          | Pairwise preferences over already feasible paths under a stated goal/budget, including use now, benefit/cost rationale and ties. Obtain reviewed or explicitly consented judgments; distinguish subjective preferences from factual feasibility. These labels are a later requirement for ranking, not assumed available from suitability labels.                                                                                                                                     |

Legitimate APIs, permitted scraping/TDM, original observations and consented contributions are candidate input routes only, subject to the separate [collection, retention, training and redistribution reviews](../legal/third-party-assets.md#proposed-strategic-data-and-training-review-task-008). No external collection or provider contact occurs in Task 008. Publicly visible metadata can supply features; it does not supply trustworthy utility labels. Existing inventory tags and appraisal percentages are not ground truth. Pseudo-labels from a deterministic rule cannot serve as independent evidence that a model improves on that rule. Store label rubric/version, reviewer method, consent/rights scope, source revisions/digests, uncertainty and exclusion reasons in a future dataset card. Default screenshot retention stays off; training contribution is a separate explicit choice.

### Narrow first learning objective

Learn only whether a confirmed current or deterministically reachable state is suitable as **ATTACKER for one fixed, named PvE context**. This is a binary suitability task initially; the domain remains multi-label so future independently validated roles can coexist. Do not infer a universal attacker score across all encounters. Do not learn costs, target levels, next tags or arbitrary action sequences.

Inputs: validated context-specific features computed from reviewed facts, confirmed identity/form, relevant moves and level/stat evidence, applicable individual properties and deterministic performance summaries against the declared goal. Include missingness indicators for allowed optional fields; required missing fields trigger abstention before inference. Do not use UUIDs, user names, screenshots, assigned tags, progress reports or label-generating outputs as features. Goal budgets constrain the deterministic feasible set; the first model does not learn spending preferences.

Compare regularized logistic regression and a shallow decision tree against (1) a trivial prevalence baseline and (2) the strongest simple deterministic baseline: reviewed mechanics/performance calculation with an explicit contextual suitability rule, followed by feasible-path generation and transparent benefit/cost ordering. Select/tune the strongest simple rule on development data fairly, not a deliberately weak CP/IV threshold. All candidates receive equivalent permitted inputs. If a learned component supplies no demonstrated benefit or suitable labels are unavailable, ship deterministic-only. Later path ranking requires independently reviewed preference labels and a new evaluation decision.

The learned component may return a bounded score, confidence/uncertainty and abstention reason. Deterministic logic still validates facts, prerequisites and availability, calculates targets/costs, enforces protections and hard budgets, sequences paths and selects their first actionable step. Explain a score through validated features and model limits; never present an unsupported causal explanation. Unavailable, incompatible, out-of-distribution or low-confidence inference falls back to the baseline or abstains when the baseline also lacks evidence.

### Evaluation matrix

| Surface                    | Proposed evidence and metrics                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Role suitability           | Precision/recall/F1 and PR-AUC per role, macro/micro aggregates for the eventual multi-label task, Hamming loss and sample counts/prevalence. Report current and potential states separately; for the first binary role report its positive-class metrics without implying other roles were tested. Include calibration (for example Brier score/reliability bins), abstention coverage and error at retained coverage. Unknown labels are excluded from scored positives/negatives and reported separately. |
| Next action                | Independently reviewed acceptable-action sets, including use now, no tag, missing-data guidance and untagged move changes. Measure agreement with an acceptable first action, harmful/unsupported action rate and errors by prerequisite type; multiple reasonable paths need not have identical tags.                                                                                                                                                                                                       |
| Roadmap correctness        | Validate every emitted path for legal identity transitions, move acquisition/availability, target reproducibility, prerequisite ordering, required/optional distinctions and conditional branch satisfaction. Count infeasible paths and violations by cause, separately from suitability accuracy. A predicted tag alone validates none of these.                                                                                                                                                           |
| Budget and usefulness      | Per-resource compliance using full chosen-path costs (no mixing exclusive alternatives), explicit unknown-cost blocking, protection compliance and independent rubric-based review of goal attainment, cost/benefit explanation, use-now/cheaper alternatives and limited-investment choices. Test zero/unknown/exhausted budgets; never sum incomparable resources without an explicit user tradeoff.                                                                                                       |
| Missing data and lifecycle | Required-field removal, unresolved forms, unknown mechanics/costs, invalid model, changed observations/goals/resources and every version update. Measure unsupported confident answers and abstention correctness. Test progress reports without verified observations, conflicts and restart staleness separately from model quality.                                                                                                                                                                       |
| Runtime and fallback       | Measure cold/warm inference plus full planner p50/p95 latency, peak memory and artifact/package size on specified supported Windows hardware. Proposed initial inference budgets: p95 under 100 ms warm and under 50 MiB additional peak memory; these are unmeasured targets to ratify before experimentation. Demonstrate no network requirement, deterministic output/fallback and safe absence/corruption/timeout behavior.                                                                              |

Group splits by connected evolution family including forms and individual variants; keep all current/future states and alternatives of the same individual together. Near-duplicate records and the same source entity across dataset versions must not cross train/test boundaries. Apply contributor grouping for contributed data where feasible and report conflicts/coverage limits. Fit preprocessing, feature selection, calibration and thresholds only within training/development groups. Freeze the holdout before model selection, retain a separate later-snapshot temporal robustness check and prevent rules/simulators or reviewers from incorporating holdout labels into baseline tuning. Version all artifacts and split manifests; labels derived from the same simulator measure agreement with that simulator, not independent game accuracy.

Report grouped-bootstrap uncertainty intervals, sample counts, role/context strata, disagreement and data coverage. Compare each model and the final hybrid system with the strongest deterministic baseline on the same untouched cases; evaluate action and plan quality even when suitability scores improve. A small, inconclusive or unrepresentative holdout is insufficient for an accuracy claim.

Proposed release gates, to freeze before looking at held-out results: no observed prerequisite, hard-budget or protection violations in the release suite; correct abstention on all required-input-removal fixtures; no harmful-action regression against the baseline; and a predeclared practically useful suitability improvement with uncertainty supporting that claim. Define the numeric suitability/action tolerances and minimum context coverage in the S6 experiment protocol after examining development-label quality, before opening the holdout. Zero observed failures does not prove absence of failures. No gate is achieved by Task 008, and optional hybrid inference waits until all gates and offline resource limits pass.

Keep the authorized labelled OCR/layout benchmark independent: it tests extraction from images, whereas strategic evaluation consumes confirmed structured observations. Do not inflate strategic sample counts with repeated screenshots or present fictional fixture success as real game accuracy.
