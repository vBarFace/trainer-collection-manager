# Fictional utility contracts (S1)

S1 implements version `utility-1` as isolated native types/validation in `src-tauri/src/utility.rs` and matching renderer types in `src/utility-contracts.ts`. The public Rust module makes the contracts testable; no production command, inventory DTO, renderer entry point or planner consumes them. [ADR 0007](../decisions/0007-individual-progression-roadmaps.md) and the [PRD](../product/PRD.md#utility-classification-and-progression-roadmaps--proposed) remain the product/design authority. This document records only the implemented wire contract and limits.

## Association and evidence

An assessment names exactly one canonical lowercase UUID v4 and one goal/context. Every alternative repeats the same UUID and goal ID, so `Assessment::load(bytes, expected_pokemon_id)` / `validate(expected_pokemon_id)` can reject accidental cross-individual association. Current usefulness, nullable current/potential role assessments, explicit unsupported roles, readiness and validity are distinct fields. Null role lists mean unknown; empty lists mean known-empty. Potential preparation never proves current readiness.

`provenance.evaluated` identifies the inputs used by this result; `provenance.current` supplies current revision/version references for comparison. The root goal/constraints and paths describe the evaluated snapshot, including when stale. Revisions, resource budgets and estimated costs are canonical nonnegative decimal **strings** through Rust/JSON/TypeScript, covering `0` through `9223372036854775807` without JavaScript integer rounding. The isolated S1 module performs no revision mutation or input confirmation.

S2.1 separately adds native inventory `strategic_observation_revision` / JSON/TypeScript `strategicObservationRevision`, using that same nonnegative decimal-string range, plus saved CP correction. Migration 6 initializes existing/new individuals to 0; actual CP, IV and confirmed identity query changes advance it, while appraisal, no-ops, tags, labels and dataset/provenance refreshes do not. CP correction compares expected CP and revision atomically; overflow rejects the write. This inventory infrastructure does not connect `utility-1` to production evaluation or persist fictional results. Goal, budget and protection revisions remain deferred until those concepts exist. See the [implemented observation contract](../architecture/data-model.md#saved-cp-and-strategic-observations-s21).

Contexts include observation and constraint revisions, ruleset version, nullable dataset namespace/version/SHA-256 lists, and explicit `{ "mode": "deterministic_only" }`. Dataset null means unknown, `[]` means no dataset consumed. No learned model mode or artifact is supported. Active evolution targets must name a namespace in evaluated dataset provenance. Recording a digest is not evidence of authentic data, rights or game accuracy.

Current/blocked results require equal evaluated/current context; stale results require a mismatch. Non-current results require a reason and expose no suggested action or summary tag. Historical paths and user action reports remain available as context. Comparing supplied contexts is structural consistency only: the caller supplies them; this module does not discover updates or implement invalidation/storage.

## Paths, actions and budgets

- Exactly one existing path is selected from 1–4 alternatives. Step IDs are unique across the entire assessment, and prerequisite IDs must name distinct earlier steps in the same path. This excludes missing, forward, self, cross-path and cyclic links without a graph/workflow engine.
- Preparation paths contain investment actions followed by required use of the goal role. A use-now path contains only role use with known zero investment; a wait path contains evidence guidance. Required/optional flags and explicit conditions remain separate from ordering. Ordinary future prerequisites do not block an otherwise valid first action.
- The S1 next action refers to the **first** step of the selected preparation path. It must have known satisfied/empty conditions; action reports cannot skip it. Progress reconciliation is deferred. `EVOLVE` / `POWER UP` summaries must match that action. Required move changes have a typed action but no invented default tag. Use now summarizes its supported current role. Required missing evidence or unknown/unmet use conditions prevent a current role summary.
- Current investment also requires a supported potential role, no missing required evidence, declared known affordability, and explicit evolution permission for an evolution path. Blocked/invalid paths may retain conflicting or unknown inputs while withholding suggestions. Unsupported roles never masquerade as absent tags or assessed roles. No assigned-tag field is accepted.
- Estimated costs are totals **for each alternative**, not derived game costs or a sum across alternatives. Null cost lists mean unknown; `[]` is known no cost. A null amount means that resource amount is unknown; `"0"` means known zero. A missing budget resource means unknown, never zero. Known zero-cost use now can remain available with an unknown/zero investment budget.
- Affordability validation checks consistency of the declared per-path totals against supplied per-resource budgets only. Unknown costs cannot support within/over-budget claims, and positive costs require known budgets. It does not calculate costs, reserve shared collection resources, establish path feasibility or choose a path.

Evolution targets name a dataset/species/form; power-up targets carry a finite ordered measurement range, units, goal context and rationale. S1 measurements are JSON numbers restricted to 0–1,000,000, supporting fractional fictional units while excluding unsafe integer magnitudes, infinities and reversed ranges. These are contract bounds, not Pokémon GO limits. No observed CP field or full-range CP transport is added; existing CP string contracts are unchanged. An evolution target is not a validated evolution relationship.

`actionReports` contains only a path/step reference and the observation/constraint revisions at report time. Reports do not contain a completion flag, confirmed new observations or actual spending. They can preserve stale evidence without advancing a suggestion. Storage, replay, observation confirmation and S4 reconciliation are absent.

## Bounds and errors

The bounded JSON entry point rejects documents over 128 KiB before parsing. Each plan has at most 4 alternatives, each path 8 steps, and other lists 16 items (prerequisites at most 8). Prose is trimmed 1–500 Unicode scalar values without control characters. Identifiers are 1–64 ASCII lowercase letters/digits/`_`/`-`/`:`, starting with a letter/digit; version tokens additionally permit uppercase and `.` but not `:`. SHA-256 strings are exactly 64 lowercase hexadecimal characters. Empty arrays are valid where their meaning is known-empty; nullable fields must be explicitly supplied. Unknown fields, versions and enum values are rejected. String enums reject Serde's alternate object representation, and the model object rejects extra fields rather than discarding provenance.

These small bounds limit memory, iteration and review complexity; they do not claim game limits. Validation is pure and reports a field/index path and useful reason; parse failures additionally report the Serde error. `load` enforces both encoded-size and domain bounds; typed callers can use `validate` for domain bounds. Neither function accesses storage, network or a game account.

## Shared acceptance evidence and deferred behavior

[Original fictional fixtures](../../tests/fixtures/utility/README.md) are loaded by native serialization/validation tests and renderer shape tests. They cover evolution-first, usable now with optional investment, power-up-first, missing identity/moves/mechanics, zero budget, unknown budget/costs, protection conflict, stale context/report evidence and a required untagged move change. Native negative mutations cover associations, IDs/links, vocabulary, versions, precision/ranges, bounds, unsupported data and contradictory suggestions. Renderer test-only field maps are tied to TypeScript DTO keys and check the same JSON, nulls and lossless integer strings; they are not a production parser.

This validates result shape and stated internal consistency only. Beyond S2.1's saved CP correction and observation revision, remaining observation/goal/resource/protection inputs, real role suitability, mechanics, target justification, cost estimation, progress reconciliation, roadmap persistence, strategic UI and ML remain S2–S7 work. Task 007's adapter and empty production reference catalog are unchanged. See the [delivery roadmap](roadmap.md#proposed-delivery-backlog) and [validation log](validation.md).
